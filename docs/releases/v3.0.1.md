# cl-revenue-ops v3.0.1

## Fee and admission correctness maintenance

This fixes-only release is based on v3.0.0, not on the development branch.
It backports three independently reproduced corrections without adding fee
modes, changing defaults, or claiming a measured earnings improvement.

### Fixes

- **Liquidity-safe HTLC maximum:** the preferred 10,000-sat floor no longer
  overrides channel capacity or the existing 85%-of-spendable bound. The
  protocol minimum is still respected; at exhaustion, that minimum is not a
  promise of executable liquidity. Normal admission refresh reopens the valve
  when liquidity returns. Backported from `5d3242b`.
- **Fresh fee evidence:** a governed fee decision invalidates the shared
  channel-reporting cache before taking its channel snapshot, avoiding stale
  execution-liquidity decisions after forwarding or refills. Failed fresh reads
  do not reuse stale liquidity. Backported from the applicable part of `da61cb3`.
- **Independent fee thresholds:** necessary HTLC-maximum maintenance no longer
  bypasses the existing fee-change thresholds. Suppressed fee targets remain
  pending and can cross the ordinary thresholds on later eligible evidence.
  Hard fee rails, critical-state exceptions, dry-run behavior and truthful
  applied-fee reporting remain enforced. Backported from `aa79eba`.

### Scope and compatibility

Core Lightning v26.06.7+ and Python 3.10+ requirements are unchanged. There is
no database migration, new dependency, public RPC, configuration option or
default change relative to v3.0.0. Revenue Ops remains standalone, using local
evidence only, with no Sling or external coordinator dependency.

Yield-aware pricing and its inventory-wake feature are deliberately absent.
The two-sided wake correction on development `main` applies to that newer
feature and is not applicable to this maintenance branch. Uncommitted pricing
experiments and unrelated operator work are not included.

The same applicable fixes have already been deployed on the operator's newer
development revision in incumbent `undercut` mode. This tag is a separate
v3.0.0-based release, not a claim that production runs this exact tag. Publishing
it does not require a production downgrade or activating yield-aware mode.

### Validation and limitations

Regression coverage includes exhausted/refilled channels, protocol minimums,
malformed or missing evidence, fresh-read RPC failures, fee/admission threshold
composition, pending-target convergence, dry runs, failed execution, hard rails,
and read-only/architecture guards. The exact release's test results are
recorded in the GitHub release publication notes.

This is a correctness release, not evidence of greater production earnings or
superiority over competitors. It does not eliminate gossip delays, native
policy-grace limitations, future liquidity changes, or sender-learned route
constraints. Continue monitoring ordinary forwarding and profitability.

### Upgrade and recovery

Use the explicit `v3.0.1` tag and the README upgrade instructions. Back up the
database and configuration, preserve local changes, confirm no active rebalance
jobs, then restart only Revenue Ops. Verify `revenue-status`, `revenue-health`
and configuration readback afterward; those checks do not trigger action RPCs.
Keep the existing fee mode, fee rails and budgets unless independently approved.

For v2 installations, follow the breaking-change and config-cleanup instructions
in [v3.0.0](v3.0.0.md) first. If a code rollback is needed, retain the current
database so newer settlements are not lost; do not overwrite it with an old
backup merely to revert source code.
